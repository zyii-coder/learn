# 任务资源 REST 接口设计（草稿 v0.1）

> 状态：**草稿，待评审**。标记 `❓` 的条目需要业务方确认，见文末「待确认清单」。

## 1. 范围与假设

- 设计对象：**任务（Task）** 这一资源的增、删、改、查四个接口。
- 术语：文中「资源」均指任务实体；「任务资源」= REST 语义下的 task resource。
- 不在本次范围：子任务、评论、附件、任务列表（Project）等关联资源。
- 读者：前后端对接方、测试、后续迭代维护者。

## 2. 通用约定

| 项 | 约定 | 理由 |
|---|---|---|
| Base URL | `https://{host}/api/v1` | 版本号放路径，便于后续平滑升级 |
| 资源路径 | `/tasks`，复数、全小写 | REST 惯例，集合用复数 |
| 传输格式 | JSON，`Content-Type: application/json; charset=utf-8` | — |
| 时间格式 | RFC 3339，UTC，如 `2026-11-15T02:30:00Z` | 避免时区歧义；日期型字段用 `2026-11-15` |
| ID 类型 | 不透明字符串，服务端生成（建议 ULID） | 不暴露自增规律；客户端不得解析 ID |
| 认证 | `Authorization: Bearer <token>` | 所有接口强制 |
| 字段命名 | 小驼峰 `camelCase` | 与前端习惯一致 |
| 空值语义 | 字段缺省 = 不提供；显式 `null` = 清空该字段 | 区分「没改」和「改成空」 |

### 2.1 统一错误响应

所有 4xx/5xx 返回同一结构，便于前端统一处理：

```json
{
  "code": "TASK_TITLE_REQUIRED",
  "message": "标题不能为空",
  "details": [
    { "field": "title", "reason": "must not be blank" }
  ],
  "traceId": "01JCM9X8K2QW7N3P5R7T9V2B4C",
  "timestamp": "2026-11-15T02:30:00Z"
}
```

- `code`：稳定的大写枚举，**前端按它做分支**，不要匹配 `message` 文本。
- `message`：给人看的说明，允许后续措辞调整。
- `traceId`：贯穿日志，排查问题时让用户报这个值。

### 2.2 数据模型

`Task` 资源字段：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `id` | string | 否 | 服务端生成 | 只读，客户端提交时忽略 |
| `title` | string | **是** | 1–120 字符，去首尾空白后非空 | 任务标题 |
| `description` | string | 否 | ≤ 5000 字符 | 详情；列表接口不返回该字段 |
| `status` | enum | 否 | `TODO` / `IN_PROGRESS` / `DONE` / `CANCELLED`，默认 `TODO` | 任务状态 |
| `priority` | enum | 否 | `LOW` / `MEDIUM` / `HIGH` / `URGENT`，默认 `MEDIUM` | 优先级 |
| `assigneeId` | string \| null | 否 | 必须是存在的用户 ID | 负责人；`null` 表示未分配 |
| `dueDate` | string \| null | 否 | `YYYY-MM-DD`，不得早于创建日期 ❓ | 截止日期 |
| `tags` | string[] | 否 | ≤ 10 个，每个 ≤ 20 字符，去重 | 标签 |
| `createdAt` | string | 否 | 服务端生成 | 只读，RFC 3339 |
| `updatedAt` | string | 否 | 服务端生成 | 只读，RFC 3339 |
| `version` | integer | 否 | 从 1 开始，每次修改 +1 | 只读，用于乐观锁 |

**完整资源示例**

```json
{
  "id": "01JCM9X8K2QW7N3P5R7T9V2B4C",
  "title": "完成接口文档初稿",
  "description": "覆盖任务资源的四个接口，含错误码与示例",
  "status": "IN_PROGRESS",
  "priority": "HIGH",
  "assigneeId": "u_1024",
  "dueDate": "2026-11-20",
  "tags": ["文档", "接口"],
  "createdAt": "2026-11-15T02:30:00Z",
  "updatedAt": "2026-11-15T06:12:41Z",
  "version": 2
}
```

## 3. 接口一：新增任务

**`POST /api/v1/tasks`**

创建一条任务，服务端生成 `id`、`createdAt`、`updatedAt`、`version`。

### 请求头

| 头 | 必填 | 说明 |
|---|---|---|
| `Authorization` | 是 | `Bearer <token>` |
| `Content-Type` | 是 | `application/json` |
| `Idempotency-Key` | 否 | 客户端生成的唯一键（建议 UUID）。同一键 24 小时内重复提交返回**首次**结果，防止网络重试产生重复任务 |

### 请求体

```json
{
  "title": "完成接口文档初稿",
  "description": "覆盖任务资源的四个接口，含错误码与示例",
  "priority": "HIGH",
  "assigneeId": "u_1024",
  "dueDate": "2026-11-20",
  "tags": ["文档", "接口"]
}
```

只读字段（`id` / `createdAt` / `updatedAt` / `version`）即使传入也会被忽略，不报错——避免客户端因版本差异反复失败。

### 响应 `201 Created`

响应头带 `Location: /api/v1/tasks/01JCM9X8K2QW7N3P5R7T9V2B4C`，响应体为**完整资源**（同 2.2 示例）。

### 状态码

| 码 | 场景 | 响应体 |
|---|---|---|
| `201` | 创建成功 | 完整资源 |
| `400` | 请求体 JSON 非法 / 枚举值不合法 | 统一错误体 |
| `401` | 未认证或 token 过期 | 统一错误体 |
| `422` | 字段校验失败（标题为空、超长等） | 统一错误体 + `details` |
| `409` | `Idempotency-Key` 相同但请求体不同 | 统一错误体，`code=IDEMPOTENCY_KEY_REUSED` |

### 示例

```bash
curl -X POST https://api.example.com/api/v1/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6f1c2a9e-3b7d-4c8a-9f10-2e5b7c4d1a88" \
  -d '{"title":"完成接口文档初稿","priority":"HIGH"}'
```

**422 示例**

```json
{
  "code": "TASK_TITLE_REQUIRED",
  "message": "标题不能为空",
  "details": [{ "field": "title", "reason": "must not be blank" }],
  "traceId": "01JCM9X8K2QW7N3P5R7T9V2B4C",
  "timestamp": "2026-11-15T02:30:00Z"
}
```

## 4. 接口二：查询任务

**`GET /api/v1/tasks`**

按条件分页查询任务列表。只读，无副作用。

### 查询参数

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `page` | integer | 否 | `1` | 页码，从 1 开始 |
| `pageSize` | integer | 否 | `20` | 每页条数，1–100；超过 100 按 100 处理 ❓ |
| `status` | string | 否 | — | 多值用逗号分隔：`status=TODO,IN_PROGRESS` |
| `priority` | string | 否 | — | 同上 |
| `assigneeId` | string | 否 | — | 按负责人过滤；`assigneeId=none` 表示查未分配 |
| `keyword` | string | 否 | — | 在 `title` 上模糊匹配，≤ 50 字符 |
| `dueBefore` | string | 否 | — | `YYYY-MM-DD`，查截止日期早于该日期的任务 |
| `sort` | string | 否 | `createdAt` | 排序字段：`createdAt` / `updatedAt` / `dueDate` / `priority` |
| `order` | string | 否 | `desc` | `asc` / `desc` |

### 响应 `200 OK`

```json
{
  "items": [
    {
      "id": "01JCM9X8K2QW7N3P5R7T9V2B4C",
      "title": "完成接口文档初稿",
      "status": "IN_PROGRESS",
      "priority": "HIGH",
      "assigneeId": "u_1024",
      "dueDate": "2026-11-20",
      "tags": ["文档", "接口"],
      "createdAt": "2026-11-15T02:30:00Z",
      "updatedAt": "2026-11-15T06:12:41Z",
      "version": 2
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 137,
  "totalPages": 7
}
```

**列表项不含 `description`**：列表页用不到大字段，剔除后可显著降低响应体积。需要正文时调详情接口。

### 状态码

| 码 | 场景 |
|---|---|
| `200` | 查询成功；无匹配数据时返回空 `items: []`，**不是 404** |
| `400` | 参数非法（`pageSize=0`、`sort` 传了不支持的值、日期格式错） |
| `401` | 未认证 |

### 示例

```bash
curl -G https://api.example.com/api/v1/tasks \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "status=TODO,IN_PROGRESS" \
  --data-urlencode "keyword=接口" \
  --data-urlencode "sort=dueDate" --data-urlencode "order=asc" \
  --data-urlencode "page=1" --data-urlencode "pageSize=20"
```

### 分页方式说明

草稿先用 `page/pageSize`，实现简单、前端易对接。数据量上万后偏移分页会出现「翻页时数据漂移」和多查的性能问题，届时应换成游标分页：`?cursor=<opaque>&limit=20`，响应带 `nextCursor`。❓ 是否现在就上游标由数据规模决定。

## 5. 接口三：修改任务

**`PUT /api/v1/tasks/{id}`**

全量更新：请求体视为该任务的**完整新状态**，未传的可选字段回落为默认值（`description` 清空、`tags` 清空、`assigneeId` 置 `null`）。这是 PUT 的标准语义，也是它最容易踩坑的地方——只改标题却把标签清掉了。

> 若业务上「部分更新」是常态，应改用 `PATCH` 做字段级合并；两者可并存。❓ 见待确认清单第 3 条。

### 路径参数

| 参数 | 说明 |
|---|---|
| `id` | 任务 ID，不存在返回 404 |

### 请求头

| 头 | 必填 | 说明 |
|---|---|---|
| `Authorization` | 是 | — |
| `Content-Type` | 是 | `application/json` |
| `If-Match` | 建议 | 传上次拿到的 `version`，如 `If-Match: "2"`。不匹配返回 `412`，防止两人的修改互相覆盖 |

### 请求体

```json
{
  "title": "完成接口文档初稿（已评审）",
  "description": "补充错误码与幂等说明",
  "status": "DONE",
  "priority": "HIGH",
  "assigneeId": "u_1024",
  "dueDate": "2026-11-20",
  "tags": ["文档", "接口", "已评审"]
}
```

`id` / `createdAt` / `updatedAt` / `version` 为只读，传入忽略。

### 响应 `200 OK`

返回更新后的**完整资源**，`version` 已自增，`updatedAt` 已刷新。返回资源而非空体，可以省掉客户端一次重新查询。

### 状态码

| 码 | 场景 |
|---|---|
| `200` | 更新成功 |
| `400` | JSON 非法、枚举值不合法 |
| `401` | 未认证 |
| `403` | 无权修改该任务（非负责人且非管理员）❓ |
| `404` | 任务不存在，或已被软删除 |
| `412` | `If-Match` 与当前 `version` 不一致（并发冲突） |
| `422` | 字段校验失败 |

**412 响应体**应带上当前版本，方便客户端合并后重试：

```json
{
  "code": "TASK_VERSION_CONFLICT",
  "message": "任务已被他人修改，请刷新后重试",
  "details": [{ "field": "version", "reason": "expected 2, actual 3" }],
  "traceId": "01JCM9X8K2QW7N3P5R7T9V2B4C",
  "timestamp": "2026-11-15T06:15:02Z"
}
```

### 示例

```bash
curl -X PUT https://api.example.com/api/v1/tasks/01JCM9X8K2QW7N3P5R7T9V2B4C \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H 'If-Match: "2"' \
  -d '{"title":"完成接口文档初稿（已评审）","status":"DONE","priority":"HIGH"}'
```

## 6. 接口四：删除任务

**`DELETE /api/v1/tasks/{id}`**

删除任务。**幂等**：重复调用不报错，结果一致。

### 请求头

| 头 | 必填 | 说明 |
|---|---|---|
| `Authorization` | 是 | — |
| `If-Match` | 否 | 传 `version` 可避免删掉别人刚改过的任务 |

### 响应 `204 No Content`

无响应体。

### 状态码

| 码 | 场景 |
|---|---|
| `204` | 删除成功；任务此前已删除也返回 204（保证幂等） |
| `401` | 未认证 |
| `403` | 无权删除（仅创建者或管理员可删）❓ |
| `404` | ID 从未存在过 |
| `409` | 存在未完成的子任务或依赖，禁止删除 ❓ |

> **已删除与不存在要区分开**：`404` 只用于「这个 ID 从来没有过」，重复删除返回 `204`。否则客户端重试逻辑会误判失败。

### 软删除策略（建议）

- 删除只置 `deletedAt`，列表/详情/修改接口一律过滤掉已删除记录，对客户端表现为真删除。
- 保留 7 天，期间可通过后台或扩展接口 `POST /api/v1/tasks/{id}/restore` 恢复。
- 超期由定时任务物理删除。

理由：误删是高频事故，硬删除不可逆；软删除的代价只是多一个过滤条件和一张表的存储。

### 示例

```bash
curl -X DELETE https://api.example.com/api/v1/tasks/01JCM9X8K2QW7N3P5R7T9V2B4C \
  -H "Authorization: Bearer $TOKEN" \
  -w "%{http_code}\n"
```

## 7. 四个接口速查

| 操作 | 方法与路径 | 成功码 | 幂等 | 请求体 | 响应体 |
|---|---|---|---|---|---|
| 新增 | `POST /api/v1/tasks` | `201` | 否（靠 `Idempotency-Key`） | 任务字段 | 完整资源 + `Location` |
| 查询 | `GET /api/v1/tasks` | `200` | 是 | 无 | 分页列表（无 `description`） |
| 修改 | `PUT /api/v1/tasks/{id}` | `200` | 是 | 完整任务字段 | 完整资源 |
| 删除 | `DELETE /api/v1/tasks/{id}` | `204` | 是 | 无 | 空 |

## 8. 权限模型（草案）

| 角色 | 新增 | 查询 | 修改 | 删除 |
|---|---|---|---|---|
| 创建者 | ✅ | ✅ | ✅ | ✅ |
| 负责人 | ✅ | ✅ | ✅ | ❌ |
| 项目成员 | ✅ | ✅ | ❌ | ❌ |
| 管理员 | ✅ | ✅ | ✅ | ✅ |

❓ 是否需要「负责人可改但不可删」这类细粒度规则，取决于产品定义。

## 9. 落地到 Spring Boot 的映射参考

若按 Spring Boot 实现，四个接口对应：

| 接口 | 注解组合 |
|---|---|
| 新增 | `@PostMapping("/tasks")` + `@Valid @RequestBody TaskCreateRequest`，返回 `ResponseEntity.status(201).header("Location", ...)` |
| 查询 | `@GetMapping("/tasks")` + `@ModelAttribute TaskQuery`（或逐个 `@RequestParam`） |
| 修改 | `@PutMapping("/tasks/{id}")` + `@PathVariable` + `@RequestHeader(value="If-Match", required=false)` |
| 删除 | `@DeleteMapping("/tasks/{id}")` + 返回 `ResponseEntity.noContent().build()` |

配合 `@RestControllerAdvice` 统一异常映射到 2.1 的错误体，`@Valid` 的 `MethodArgumentNotValidException` 转 `422` + `details`。
